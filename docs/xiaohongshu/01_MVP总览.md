## 正文

很多人刚接触量化，会下意识把它想成“写一个公式，然后让程序自动赚钱”。

但我想先把口径放清楚：这个系列不是荐股，也不是实盘下单教程，而是从一个代码仓库出发，拆一条量化研究主流程。

量化可以先简单理解成：用数据、规则和程序，去做投资研究和交易验证。

比如用历史价格算动量，用财务数据算估值，用 IC 看因子有没有预测味，再用回测看一套规则历史上怎么表现。

我这里配套的代码仓库叫 `Quant Strategy`。它不是完整实盘系统，而是一个 MVP（Minimum Viable Product，最小可运行版本）量化研究工程。

仓库地址：

```text
https://github.com/xuyafei/quant_strategy
```

MVP 是 Minimum Viable Product，也就是“最小可运行版本”。放到量化工程里，就是先不追求大而全，先做一条能从数据跑到结果的最小链路。

这个仓库先固定这条主流程：

```text
数据 → 因子面板 → IC 检验 → 单因子回测 → 多因子融合
→ 组合配权 → 绩效分析 → 图表输出 → 可选落盘
```

运行命令只有一句：

```bash
python main.py
```

它会把行情读取、四因子面板、IC、单因子回测、融合回测、绩效和图表串起来。可以对照仓库里的 `main.py` 和 `docs/articles` 一起看。

为什么不一上来接实盘？

因为研究链路没稳定时，接实盘只会把问题混在一起。净值不对时，你很难判断是因子不行、数据错位、回测口径不一致，还是执行系统出了问题。

所以第一步不是接实盘，而是先把研究侧闭环跑通。MVP 最大的价值不是立刻证明“策略能赚钱”，而是先让每次实验变得可对照、可解释、可复现。

否则项目很容易变成一堆散脚本：这个脚本一个日期，那个脚本一个手续费，另一个脚本一个 `top_k`。最后净值变了，你都不知道是 alpha 变了，还是口径变了。

一句话：

**先闭合，再加厚。**

后面再讲入口配置、数据因子、IC、融合、回测配权和绩效复现。
