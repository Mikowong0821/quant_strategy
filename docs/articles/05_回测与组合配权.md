# 回测与组合配权：把一列分数翻译成持仓和净值

第四篇我们讲了 IC 和多因子融合。

到这一步，系统里已经有两类可以用于选股的分数：

```text
单因子得分：MOMENTUM / VOLATILITY / PE / ROE
融合得分：FUSED_ZSCORE
```

但因子分数本身还不是策略。

它只是回答了一个问题：

```text
同一天里，哪些股票相对更值得排在前面？
```

真正的回测还要继续回答：

```text
什么时候调仓？
买哪几只？
每只买多少钱？
手续费怎么扣？
每天净值怎么变？
如果优化器失败怎么办？
```

这就是第五篇要讲的主题：

```text
回测与组合配权
```

在当前 MVP 工程里，回测不是一个“画净值图”的函数，而是一套把分数翻译成交易路径的会计规则。

---

## 一、回测层在整个链路里的位置

前面几篇的流程可以简化成：

```text
数据 → 因子面板 → IC → 多因子融合
```

这些步骤都还停留在研究信号层。

回测从这里接过来：

```text
因子 / FUSED 得分 → Top-K → 配权 → 调仓 → 净值
```

当前单因子回测核心在：

```text
backtest/backtest_single.py
```

主要函数是：

```python
run_single_backtest(...)
```

多因子回测在：

```text
backtest/backtest_multi.py
```

但它本质上还是把融合后的一列得分交给单因子回测：

```python
run_multi_backtest(fused=...)
→ run_single_backtest(factor_values=fused_scores, ...)
```

这意味着单因子和融合策略共享同一套交易规则。

它们之间的差异主要来自：

```text
用哪一列分数排序。
```

这很重要。

如果每条曲线都偷偷使用不同的调仓频率、手续费或配权方式，你就很难比较“因子好坏”。

当前 MVP 的设计是：

```text
规则统一，分数不同。
```

这样单因子线和融合线才有可比性。

---

## 二、回测不是预测，而是模拟账户变化

`run_single_backtest` 内部维护两个核心状态：

```text
cash
shares
```

初始状态很简单：

```text
cash = 1.0
shares = 0
```

也就是期初净值归一化为 1。

每天先用当日价格估算账户价值：

```python
nav = _portfolio_value(cash, shares, px)
```

`_portfolio_value` 做的事情也很直接：

```text
现金 + 当前持仓市值
```

所以净值曲线不是凭空算出来的。

它来自一条实际的账户路径：

```text
持有什么股票
每只有多少股
还剩多少现金
当日价格是多少
```

这也是为什么回测日志很重要。

一条净值曲线只能告诉你结果，不能告诉你路径。

路径错了，结果再漂亮也不可靠。

---

## 三、什么时候调仓？

调仓频率来自配置：

```text
settings.rebalance_freq
```

默认是：

```text
ME
```

也就是月末口径。

代码里会先把旧的 pandas 频率别名做一次映射：

```python
{"M": "ME", "Q": "QE", "A": "YE", "Y": "YE"}
```

然后基于价格宽表生成调仓日期：

```python
rebalance_dates = prices_wide.resample(rf).last().index.intersection(prices_wide.index)
```

这里可以先抓住直觉：

```text
不是每天都重新选股。
只有进入 rebalance_dates 的日期，才触发选股和调仓。
```

非调仓日只做一件事：

```text
按已有持仓和当日价格估值。
```

这个区别很关键。

如果每天都按因子重新选 Top-K，换手率会非常高，手续费和执行假设也会完全不同。

在 MVP 阶段，默认用月末调仓，是为了让流程简单、稳定、容易解释。

---

## 四、调仓日如何选 Top-K？

到了调仓日，回测会取出当天的因子截面：

```python
sc = factor_values.xs(dt, level=0)
```

然后做几步处理：

```text
1. 去掉缺失因子值
2. 按因子值降序排序
3. 过滤掉价格无效的股票
4. 取前 top_k 只
```

对应配置是：

```text
settings.top_k
```

默认是 5。

所以 Top-K 只回答一个问题：

```text
这一期买哪几只？
```

它不回答每只买多少钱。

这就是后面组合配权要解决的问题。

这里还有一个前面几篇反复强调的约定：

```text
因子值越大，越优先进入 Top-K。
```

所以第三篇里才要把波动率和 PE 做方向处理：

```text
VOLATILITY = -vol
PE = -pe
```

否则回测层统一降序排序时，含义会乱。

---

## 五、先卖后买：为什么调仓要像会计账？

选出 Top-K 后，系统要把当前持仓调整到目标持仓。

当前 MVP 的调仓逻辑是：

```text
先卖后买
单边手续费
现金不足时按比例缩买入
```

代码里有两个调仓函数：

```python
_rebalance_topk_equal_weight(...)
_rebalance_to_target_weights(...)
```

等权时用第一个。

最大夏普和风险平价得到目标权重后，用第二个。

两者底层思路类似：

```text
1. 先计算调仓前账户净值 nav0
2. 根据目标权重算每只股票目标市值
3. 先卖出超过目标市值的部分
4. 扣卖出手续费
5. 再买入低于目标市值的部分
6. 扣买入手续费
7. 如果现金不够，买入金额按比例缩放
```

这里的手续费来自：

```text
settings.commission_rate
```

默认是：

```text
0.0003
```

也就是单边 3 个基点。

当前 MVP 没有模拟滑点、涨跌停、成交量约束、最小交易单位，也没有真实撮合。

成交口径简化在日频收盘价框架里。

这不是说这些细节不重要。

而是 MVP 先把主流程跑通：

```text
分数 → 选股 → 配权 → 交易成本 → 净值
```

等这条链稳定之后，再逐步加滑点、流动性、停牌、涨跌停等更真实的约束。

---

## 六、组合配权：Top-K 之后，钱如何分？

Top-K 只解决：

```text
买哪几只？
```

组合配权解决：

```text
每只买多少钱？
```

当前工程通过配置控制：

```text
settings.portfolio_weighting
```

支持三种方式：

```text
equal
max_sharpe
risk_parity
```

它们都只在已经选出的 Top-K 股票内部工作。

这条边界非常重要：

```text
因子负责选股。
配权负责分资金。
```

配权优化不会跑回去重新决定买哪几只股票。

---

## 七、等权：最简单，也最稳的基线

等权是：

```text
每只股票 = 1 / K
```

如果 Top-K 是 5 只，每只目标权重就是 20%。

等权的优点是：

- 简单。
- 透明。
- 不依赖收益均值和协方差估计。
- 很适合作为回测基线。

很多时候，等权不是“低级版本”，而是一个非常重要的对照组。

如果一个复杂优化方法长期跑不赢等权，就要怀疑它是不是真的带来了增益。

当前代码里，如果 `portfolio_weighting` 是 `equal`，或者可选标的少于 2 只，都会直接使用等权。

---

## 八、最大夏普：用历史收益估计 μ 和 Σ

如果配置为：

```text
portfolio_weighting = "max_sharpe"
```

回测会在每个调仓日，对已选出的 Top-K 股票估计：

```text
μ：历史日均收益向量
Σ：历史收益协方差矩阵
```

估计窗口来自：

```text
settings.optimizer_return_window
```

默认是 60。

最低样本数来自：

```text
settings.optimizer_min_obs
```

默认是 15。

如果有效历史样本不足，就不会硬做优化，而是回退等权。

如果样本够，就调用：

```python
maximize_sharpe(mu, cov, risk_free=0.0)
```

目标是最大化：

```text
(μ - rf)'w / sqrt(w'Σw)
```

并且默认是仅做多、权重和为 1。

这里要特别注意：

```text
调仓时最大化的夏普
```

和绩效报告里的：

```text
已实现净值夏普
```

不是同一个东西。

前者是当时用历史样本估出来的优化目标。

后者是回测结束后，对整条净值曲线算出来的成绩单。

名字都叫夏普，但所在层级不同。

---

## 九、风险平价：让风险贡献更均衡

如果配置为：

```text
portfolio_weighting = "risk_parity"
```

回测同样会先估计 Top-K 股票的协方差矩阵：

```text
Σ
```

然后调用：

```python
risk_parity(cov)
```

风险平价的直觉是：

```text
不要让某一只股票贡献过多组合风险。
```

代码里使用的是 ERC，也就是等风险贡献。

它希望各资产的风险贡献尽量接近：

```text
组合波动 / 资产数量
```

相比最大夏普，风险平价不需要估计 μ。

这通常会让它对收益均值估计误差更不敏感。

但它仍然依赖协方差估计。

所以样本不足或优化失败时，外层回测会回退等权；优化器内部如果失败，也会回退到逆波动率权重。

这就是工程上的防护：

```text
优化可以失败，但回测不能静默跑歪。
```

## 十、为什么要记录 rebalance_log？

每次调仓后，回测都会记录：

```text
date
picks
weights
weighting
```

也就是：

```text
哪一天调仓？
选了哪些股票？
每只目标权重是多少？
当期用的是哪种配权方式？
```

这些信息放在：

```text
meta["rebalance_log"]
```

`main.py` 也会把它打印出来。

这比只看净值曲线重要得多。

因为净值曲线只能告诉你：

```text
结果涨了还是跌了。
```

调仓日志可以告诉你：

```text
系统到底做了什么。
```

如果某段净值突然变好，你可以回头看：

- 是否某一期持仓特别集中？
- 是否某只股票贡献很大？
- 是否优化器突然从 max_sharpe 回退到等权？
- 是否 Top-K 名单大幅切换？

这些都是排错和写研究记录时必须知道的东西。

---

## 十一、这个 MVP 回测暂时不做什么？

为了让边界清楚，也要说清楚当前 MVP 没做什么。

它暂时不做：

- 真实券商报单。
- 分钟级撮合。
- 滑点模型。
- 涨跌停和停牌细节。
- 成交量约束。
- 最小交易单位。
- 税费和不同市场费用细则。
- 复杂风控和止损规则。

这些都很重要，但它们不应该在研究链路还没稳定之前全部塞进来。

当前 MVP 的目标是先把最小闭环跑稳：

```text
得分 → Top-K → 配权 → 调仓 → 费用 → 净值 → 日志
```

这条链稳定以后，再往执行层和实盘层加厚，才更容易定位问题。

---

## 十二、这篇文章的核心结论

回测不是“把因子画成一条曲线”。

它是一套明确的账户规则：

```text
什么时候调仓？
选哪几只？
每只配多少？
怎么成交？
怎么扣成本？
怎么记录路径？
```

当前 MVP 的分层是：

```text
因子 / FUSED 得分：负责排序
Top-K：负责选股
portfolio_weighting：负责配权
调仓函数：负责现金、股份和手续费
rebalance_log：负责审计路径
nav：负责最终净值
```

最重要的一句话是：

```text
选股和配权是两件事。
```

因子决定买什么，组合优化决定买多少。

而回测引擎负责把这两件事放进一条可复现、可审计的交易路径里。
