# 入口与配置：量化工程先要有一个稳定的总开关

第一篇我们先看了整个 MVP 量化工程的轮廓。

它不是一个实盘系统，也不是一个很重的平台，而是一条已经闭合的研究链路：

```text
数据 → 因子面板 → IC 检验 → 单因子回测 → 多因子融合
→ 组合配权 → 绩效分析 → 图表输出 → 可选落盘
```

这一篇开始往代码里走。

但我不想一上来就讲动量因子怎么写，也不想先讲 IC 公式。因为在一个量化工程里，真正决定项目能不能长期迭代的，往往不是第一个公式，而是两个很朴素的问题：

```text
从哪里启动？
用哪组参数启动？
```

在这个仓库里，答案分别是：

- `main.py`：主入口，负责把研究流程按固定顺序串起来。
- `config.py`：全局配置，负责把会影响实验结果的参数集中管理。

这两个文件看起来没有太多“炫技”的地方，但它们是整个 MVP 最重要的工程骨架。

如果没有这层骨架，后面的因子、IC、回测、融合、配权都会慢慢散掉。

---

## 一、为什么量化项目很容易变成散脚本？

很多量化研究一开始都是从一个小脚本开始的。

比如先写一个脚本下载行情：

```text
download_data.py
```

再写一个脚本算动量：

```text
factor_momentum.py
```

然后写一个脚本做回测：

```text
backtest_demo.py
```

最后再写一个脚本画图：

```text
plot_nav.py
```

这在学习早期没有问题。问题出现在项目开始变复杂之后。

你会慢慢遇到这些情况：

- 数据脚本里写了一个起止日期。
- 回测脚本里又写了另一个起止日期。
- IC 脚本用的是 1 日前瞻收益。
- 回测调仓用的是月末。
- 画图脚本默认读取上一次输出的文件。
- 手续费率在某个函数里写死。
- `top_k` 今天改成 5，明天又忘了另一个地方还是 10。

这个时候，项目表面上还能跑，但结果已经开始变得危险。

因为你看到的一条净值曲线，可能并不只是策略逻辑的结果，而是很多隐藏参数共同作用的结果。

更麻烦的是，等你过两周想复现这条曲线时，你可能已经不记得当时到底改过哪些地方。

量化工程里，“能跑”只是第一步。

更重要的是：

> 每一次运行，都应该知道它是按什么流程、用什么参数、生成了什么输出。

这就是 `main.py` 和 `config.py` 要解决的问题。

---

## 二、`main.py` 不是大杂烩，而是流程编排器

当前仓库的启动方式很简单：

```bash
python main.py
```

这条命令背后，`main.py` 会按一个固定顺序执行研究链路。

从代码结构看，它大致做了这些事：

```text
1. 读取 Settings 配置
2. 获取行情数据
3. 构建四因子面板
4. 可选保存行情与因子面板
5. 对每个因子计算 IC
6. 对融合得分也计算 IC
7. 跑四条单因子回测
8. 用 IC 滞后滚动列权或等权方式生成 FUSED_ZSCORE
9. 跑融合策略回测
10. 输出 IC 图、权重图、净值对比图
```

你会发现，`main.py` 本身并不负责“把所有数学细节都写在自己里面”。

比如：

- 行情读取交给 `live/data_feed.py`
- 长表宽表转换交给 `backtest/backtest_utils.py`
- 因子面板构建交给 `factors/panel_builder.py`
- IC 计算交给 `analysis/ic.py`
- 单因子回测交给 `backtest/backtest_single.py`
- 多因子回测交给 `backtest/backtest_multi.py`
- 融合逻辑交给 `models/fusion.py`
- 配权优化交给 `models/optimizer.py`
- 绩效和作图交给 `analysis/performance.py`、`analysis/plotting.py`

所以 `main.py` 的角色不是“全都亲自算”，而是“规定大家按什么顺序合作”。

这件事在量化项目里非常重要。

因为量化研究不是只看一个函数是否正确，而是要看整条链路是否一致：

```text
数据口径一致吗？
因子日期和收益日期对齐吗？
IC 的前瞻窗口清楚吗？
回测用的是同一份价格表吗？
融合得分有没有偷看未来？
配权优化只发生在已选中的 Top-K 内吗？
绩效统计描述的是哪条净值？
```

如果入口不统一，这些问题会分散在很多脚本里。

入口统一以后，排错路径也会清楚很多。

你可以顺着 `main()` 的执行顺序看：

```text
数据是否加载成功？
因子面板是否为空？
IC 是否有有效日？
单因子是否跑出净值？
融合是否成功回退或加权？
图表是否落盘？
```

这就是工程上的“可观察性”的第一层。

## 三、这个入口具体保护了哪些边界？

`main.py` 里有几个很值得保留的边界。

### 1. 数据有兜底

主流程会优先找本地文件：

```text
data/prices_demo.csv
```

如果本地没有，就尝试用 Tushare 拉取默认股票池。

如果外部数据也不可用，就回退到合成数据。

这不是说合成数据适合做真实研究，而是说 MVP 工程应该能在没有外部依赖时也跑通。

对学习和调试来说，这个兜底非常有用。

你不会因为一时没有 token、网络失败、接口限流，就完全无法验证主流程。

### 2. 因子面板只构建一次

代码里会先调用：

```text
build_four_factor_panel(prices, long_df, settings)
```

得到统一的 `panel`。

后面的 IC、单因子回测、多因子融合，都会围绕这张因子面板展开。

这比每个模块各自重新算一遍因子更清楚。

因为一旦所有模块都共享同一个面板，你就更容易判断差异来自哪里：

- IC 差，是评价口径的问题。
- 单因子净值差，是回测规则的问题。
- 融合净值差，是列权和标准化的问题。

而不是每个脚本都暗自生成一份可能略有不同的因子数据。

### 3. IC 与回测分开

`main.py` 会先计算 IC，再跑单因子回测。

这很容易让人误解：是不是 IC 直接参与了单因子选股？

当前工程里不是。

单因子回测仍然是按该因子列在再平衡日做横截面排序，取 Top-K。

IC 主要用于两件事：

- 评价每个因子的历史预测味道。
- 在多因子融合中，作为滞后滚动列权的输入。

也就是说，IC 在这里没有直接进入 Top-K 内股票层的最大夏普或风险平价优化。

这个边界很重要。

否则你很容易把“因子评价”“选股规则”“组合配权”混在一起，最后不知道策略到底靠什么在工作。

### 4. 融合路径有明确回退

默认情况下，融合得分会尝试使用：

```text
fuse_ic_weighted_zscore
```

直觉是：先把每个因子做横截面 z-score，再用历史 IC 的滞后滚动均值作为列权，合成 `FUSED_ZSCORE`。

但代码里也保留了回退：

```text
fuse_equal_weight_zscore
```

如果配置关闭 IC 权重，或者某些因子缺 IC，或者加权过程异常，系统会回到等权 z-score。

这对 MVP 很重要。

因为早期工程不应该因为某个增强模块失败，就让整条主流程完全不可用。

增强能力可以失败，但主流程要尽量给出可解释的输出。

### 5. 输出统一收集

`main.py` 会把单因子和融合策略的净值都收集到：

```text
nav_curves
```

最后输出统一的净值对比图：

```text
output/nav_compare.png
```

如果打开 `persist_run_outputs`，还会输出：

- IC 对比图
- 单因子 IC 时间序列图
- 权重堆叠图
- 行情与因子面板缓存
- IC 序列 CSV
- 运行配置快照 `output/cache/run_config.json`
- 绩效汇总表 `output/performance_summary.csv`
- 调仓明细 `output/rebalance_logs/*.csv`

这让一次研究运行不只是“终端滚过一堆数字”，而是留下了可复盘的材料。

## 四、`config.py` 是实验条件，不只是参数文件

再看 `config.py`。

当前工程用一个只读 dataclass 管理项目级配置：

```python
@dataclass(frozen=True)
class Settings:
    project_root: Path
    data_dir: Path
    output_dir: Path
    price_col: str = "close"
    commission_rate: float = 0.0003
    rebalance_freq: str = "ME"
    trading_days_per_year: int = 252
    backtest_start: str = "2024-01-01"
    backtest_end: str = "2025-01-01"
    top_k: int = 5
    momentum_lookback: int = 20
    vol_window: int = 20
    fina_history_years: int = 2
    persist_run_outputs: bool = True
    ic_forward_days: int = 1
    fusion_use_ic_weights: bool = True
    fusion_ic_rolling_window: int = 60
    fusion_ic_min_periods: int = 20
    portfolio_weighting: str = "max_sharpe"
    optimizer_return_window: int = 60
    optimizer_min_obs: int = 15
```

这些字段不只是“方便改”。

它们共同定义了一次回测实验。

比如：

### 1. 时间区间

```text
backtest_start
backtest_end
```

决定研究样本覆盖哪里。

同一个策略，在不同市场阶段里可能完全不同。

如果时间区间散落在多个脚本里，你很难保证 IC、回测、图表用的是同一段历史。

### 2. 调仓规则

```text
rebalance_freq = "ME"
top_k = 5
commission_rate = 0.0003
```

这三个参数决定回测行为的底层口径：

- 多久调一次仓。
- 每次选多少只。
- 交易成本怎么扣。

它们不属于某个因子本身，却会显著影响最终净值。

所以它们应该集中、明确、可追踪。

### 3. 因子窗口

```text
momentum_lookback
vol_window
fina_history_years
```

这些参数决定因子如何计算。

例如动量看过去多少天，波动率用多长窗口，财务数据往前取多少年。

如果你后续要比较“20 日动量”和“60 日动量”，最好的方式不是直接在因子函数里改魔法数，而是让配置成为实验记录的一部分。

### 4. IC 口径

```text
ic_forward_days = 1
```

这个参数决定 IC 使用几日的前瞻收益。

注意它不是无关紧要的小参数。

如果你把前瞻窗口从 1 日改成 5 日，IC 衡量的问题就变了：

```text
因子是否预测下一天的横截面收益？
```

变成：

```text
因子是否预测未来五天的横截面收益？
```

这两个问题不完全一样。

### 5. 融合开关

```text
fusion_use_ic_weights = True
fusion_ic_rolling_window = 60
fusion_ic_min_periods = 20
```

这些参数控制多因子融合。

默认情况下，工程会用因子的历史 IC 滞后滚动均值做列权。

这里的关键词是“滞后”。

因为今天调仓时，不能使用今天之后才知道的信息。

如果这个开关关闭，工程会回到等权 z-score 融合。

这给了你一个很自然的对照实验：

```text
等权融合 vs IC 滚动列权融合
```

### 6. 组合配权方式

```text
portfolio_weighting = "max_sharpe"
optimizer_return_window = 60
optimizer_min_obs = 15
```

`portfolio_weighting` 控制 Top-K 内的资金分配方式。

当前支持三种：

- `equal`：等权。
- `max_sharpe`：在已选 Top-K 内用历史收益估计 μ 和 Σ，再最大化夏普。
- `risk_parity`：在已选 Top-K 内用协方差估计做风险平价。

这里要特别注意一层分工：

```text
因子分数决定买哪几只。
portfolio_weighting 决定这几只怎么买。
```

配权优化不负责重新选股。

它只在已经选中的 Top-K 股票内部决定权重。

这也是为什么 `optimizer_return_window` 和 `optimizer_min_obs` 需要配置化。它们控制历史样本窗口和最低样本数，直接影响权重是否稳定。

### 7. 输出与复现

```text
persist_run_outputs = True
```

这个开关决定是否把运行结果落盘。

打开以后，研究不再只停留在终端输出里，而是会留下 CSV 和 PNG。

对写文章、写研报、比较版本都很有用。

## 五、为什么配置要集中，而不是哪里用哪里写？

因为量化研究本质上是一种实验。

实验最怕两件事：

```text
条件不清楚。
结果不可复现。
```

如果参数散落在多个脚本里，你可能会得到一个看起来不错的结果，但无法解释它到底是在什么条件下得到的。

而集中配置至少带来三个好处。

### 1. 改动更可控

当你想比较不同 `top_k` 时，只改一个地方。

当你想比较等权、最大夏普、风险平价时，只改一个字段：

```text
portfolio_weighting
```

这让策略实验更像“做实验”，而不是“到处找变量”。

### 2. 复现更简单

如果未来要做实验记录，可以把 `Settings` 的关键字段和输出结果绑定。

例如：

```text
2026-05-07
top_k=5
rebalance_freq=ME
portfolio_weighting=max_sharpe
fusion_use_ic_weights=True
```

这样下一次看到某张净值图时，你知道它不是凭空来的。

### 3. 新人更容易读项目

对一个刚打开仓库的人来说，最友好的阅读顺序通常是：

```text
config.py → main.py → docs/FLOW_AND_MODULES.md → 具体模块
```

先看配置，知道有哪些可调条件。

再看入口，知道流程怎么走。

最后再深入某个模块，比如因子、IC 或回测。

这比一上来钻进某个函数里更不容易迷路。

## 六、Token 为什么要特殊处理？

`config.py` 里还有一个函数：

```python
def get_tushare_token() -> str:
    token = os.environ.get("TUSHARE_TOKEN", "").strip()
    if token:
        return token
    local = _TUSHARE_TOKEN_LOCAL.strip()
    if local:
        return local
    raise ValueError("请设置环境变量 TUSHARE_TOKEN，或在 config._TUSHARE_TOKEN_LOCAL 填写本地回退（勿提交）")
```

这个函数体现了一个简单但很重要的工程习惯：

```text
密钥不应该提交到仓库。
```

当前逻辑是：

1. 优先读取环境变量 `TUSHARE_TOKEN`。
2. 如果没有，再读取本地回退 `_TUSHARE_TOKEN_LOCAL`。
3. 如果还没有，就报错提示。

本地回退适合自己机器上临时跑通流程。

但如果代码要推送远程仓库，真实 token 应该清空，或者只通过环境变量注入。

这件事和 alpha 无关，但和工程可靠性有关。

一个量化项目不只要防未来函数，也要防密钥泄露。

## 七、`main.py` 和 `config.py` 的关系

可以把二者关系理解成：

```text
config.py 规定“这次实验怎么设定”
main.py 负责“按这些设定跑完整条链”
```

例如 `main.py` 一开始会调用：

```python
settings = get_settings()
```

后面所有关键步骤都会使用同一份 `settings`。

比如：

- 数据层用它拿路径和回测时间。
- 因子层用它拿动量窗口、波动率窗口、财务历史长度。
- IC 层用它拿前瞻收益天数。
- 回测层用它拿 Top-K、手续费、调仓频率、配权方式。
- 作图和缓存层用它拿输出目录和落盘开关。

这就避免了一个常见问题：

```text
每个模块都有自己的一份默认参数。
```

默认参数一多，系统就会变得难以解释。

这个 MVP 的做法是：模块可以有自己的实现细节，但实验口径尽量从同一份 `Settings` 进入。

## 八、这篇文章对应的阅读路线

如果你要读代码，可以按这个顺序：

```text
1. 先看 config.py
   看 Settings 里有哪些字段。

2. 再看 main.py 的 main()
   不需要先看每个函数实现，先看它调用了哪些模块。

3. 再看 docs/FLOW_AND_MODULES.md
   用流程图把 main.py 的调用关系可视化。

4. 最后按兴趣进入具体模块
   数据、因子、IC、回测、融合、优化、绩效。
```

如果你要改策略，也建议先从配置开始。

比如：

- 想测试更分散的持仓：先改 `top_k`。
- 想降低换手：先改 `rebalance_freq`。
- 想比较配权方式：先改 `portfolio_weighting`。
- 想看 IC 加权是否有帮助：切换 `fusion_use_ic_weights`。
- 想保留实验材料：保持 `persist_run_outputs=True`。

这比直接改函数内部逻辑更稳。

因为你能先确认：结果变化来自实验条件，而不是代码结构被改乱。

## 九、这一篇的核心结论

一个量化工程最小但重要的秩序，不是目录多漂亮，也不是公式多复杂，而是：

```text
入口唯一。
参数集中。
流程可读。
输出可复现。
```

`main.py` 和 `config.py` 做的就是这件事。

它们把这个 MVP 从“一堆可以运行的函数”变成“一条可以反复执行的研究链路”。

后面我们再讲数据层、因子层、IC、融合、回测和配权时，都要回到这条主线：

```text
每个模块都可以单独变强，
但它必须挂在同一条可复现的链路上。
```

这也是这个项目从 MVP 往专业级量化工程演进的第一步。
