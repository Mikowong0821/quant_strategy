# 数据与因子面板：量化研究先把表对齐，再谈信号

前两篇我们先确定了这个 MVP 量化工程的整体定位，以及入口和配置为什么重要。

到第三篇，才真正进入研究链路的第一层：

```text
数据 → 因子面板
```

这一层看起来不如 IC、夏普率、多因子融合那么有“策略感”，但它其实是整个系统最容易埋雷的地方。

很多回测结果不可信，不是因为因子公式多复杂，而是因为最开始的数据形态就没有统一：

- 行情日期没有对齐。
- 股票代码口径不一致。
- 因子值和价格表不是同一套交易日。
- 财务数据用了还没公告的信息。
- 某个脚本用长表，另一个脚本用宽表，中间转换口径不清楚。

这些问题不会总是直接报错。

更危险的是，它们可能让程序顺利跑完，甚至画出一条很好看的净值曲线。

所以这篇先讲一个朴素但很关键的问题：

> 在量化工程里，为什么要先把数据整理成稳定的长表、宽表和因子面板？

---

## 一、数据层不是“拿到价格”这么简单

在当前仓库里，数据入口主要在：

```text
live/data_feed.py
```

主流程 `main.py` 会优先尝试读取本地演示数据：

```text
data/prices_demo.csv
```

如果本地没有，就尝试从 Tushare 拉取默认股票池。

如果外部数据不可用，就回退到合成价格数据。

这个设计不是说合成数据能用于真实研究。它的意义是：MVP 工程必须能在没有外部依赖时跑通主流程。

对学习和调试来说，这很重要。

你应该能先验证：

```text
数据 → 因子 → IC → 回测 → 图表
```

这条链路有没有接上，而不是第一步就卡在 token、网络、接口权限上。

但是不管数据来自 CSV、Tushare 还是合成数据，进入后续模块之前，它都要变成工程认可的数据形态。

当前项目里最重要的是两种：

```text
长表 long_df
宽表 prices
```

---

## 二、长表：一天一只股票一行

长表可以理解成：

```text
trade_date | ts_code   | open | high | low | close | volume
2024-01-02 | 600519.SH | ...  | ...  | ... | ...   | ...
2024-01-02 | 000001.SZ | ...  | ...  | ... | ...   | ...
2024-01-03 | 600519.SH | ...  | ...  | ... | ...   | ...
```

也就是：

```text
一天 × 一只股票 = 一行
```

在代码里，本地 CSV 会通过：

```python
load_prices_from_csv(path)
```

读进来。

这个函数会检查基本列是否存在，比如：

```text
trade_date
ts_code
open
high
low
close
volume
```

如果 Tushare 返回的是 `vol`，也会统一改成 `volume`。

这些细节看起来很小，但它们是工程契约的一部分。

如果每个模块都自己猜列名，项目很快会变得不可维护。

长表的优势是：它很适合和“同样按股票和日期组织”的数据拼接。

比如财务指标、公告日期、基本面字段，通常更自然地按：

```text
股票代码 + 报告期 / 公告日
```

来组织。

所以 PE 和 ROE 这类因子，后面会依赖长表去做交易日网格对齐。

---

## 三、宽表：一天一行，每列一只股票

宽表可以理解成：

```text
trade_date | 000001.SZ | 600036.SH | 600519.SH
2024-01-02 | 10.12     | 33.20     | 1680.00
2024-01-03 | 10.25     | 33.70     | 1695.00
```

也就是：

```text
一天 = 一行
每只股票 = 一列
单元格 = 价格
```

当前项目里，长表转宽表用的是：

```python
long_to_wide(long_df, settings.price_col)
```

宽表最适合做两类事。

第一类是计算时间序列特征。

比如动量因子：

```python
px / px.shift(lookback) - 1.0
```

这天然就是在宽表上做列方向计算：每一列是一只股票，沿着日期往前看。

第二类是给回测日循环使用。

回测时，每天需要知道所有股票当日价格，也需要用价格矩阵计算收益、估值和调仓后的净值。

宽表在这个环节更直观。

所以这个项目同时保留长表和宽表，不是重复，而是因为它们服务不同问题：

```text
长表适合拼接和对齐。
宽表适合时序计算和回测估值。
```

---

## 四、长宽转换为什么要单独放在工具层？

长表和宽表之间的转换集中在：

```text
backtest/backtest_utils.py
```

比如：

```python
long_to_wide(...)
wide_to_long(...)
prices_to_wide_close(...)
to_returns(...)
```

这些函数看似只是 `pivot`、`stack`、`pct_change` 的薄封装，但它们有一个更重要的作用：

```text
把数据形态转换的口径固定下来。
```

如果你在每个因子脚本、每个回测脚本里都手写一次 pivot，迟早会出现细小差异：

- 有的地方排序了，有的地方没排序。
- 有的地方列名叫 `symbol`，有的地方叫 `ts_code`。
- 有的地方索引是字符串日期，有的地方是 datetime。
- 有的地方丢缺失值，有的地方保留缺失值。

这些差异会在后面放大。

所以工具层不是为了显得“工程化”，而是为了减少隐性口径漂移。

在量化项目里，很多 bug 不来自复杂算法，而来自这些小小的数据形态差异。

---

## 五、因子面板：把所有信号放到同一张表里

有了价格和长表之后，第三篇真正要落到因子面板。

当前项目里，统一构建因子面板的函数是：

```python
build_four_factor_panel(prices, long_df, settings)
```

它位于：

```text
factors/panel_builder.py
```

返回结果是一张 DataFrame：

```text
index: MultiIndex(date, symbol)
columns: MOMENTUM / VOLATILITY / PE / ROE
```

可以想象成：

```text
date       symbol     MOMENTUM  VOLATILITY  PE      ROE
2024-01-31 000001.SZ  0.035     -0.21       -8.5    12.3
2024-01-31 600519.SH  0.012     -0.18       -25.1   31.0
2024-02-29 000001.SZ  ...
```

它表达的是：

```text
某一天，某只股票，在多个因子上的得分。
```

后面的 IC、单因子回测、多因子融合，都围绕这张 panel 工作。

这件事非常关键。

因为只有当所有因子都进入同一张表，后面才有办法做统一比较：

- 同一天的不同因子能不能横向比较？
- 同一个因子在不同日期上的有效样本有多少？
- 多因子融合时，每列是不是同一套索引？
- 回测选股时，因子值和价格是不是能对上？

如果每个因子各自输出一份独立文件，后面很容易变成“文件很多，关系不清”。

因子面板的意义，就是把这些关系先钉住。

---

## 六、四个默认因子分别是什么？

当前 MVP 默认构建四列因子：

```text
MOMENTUM
VOLATILITY
PE
ROE
```

它们不是为了证明“这四个就是最优因子”，而是为了覆盖几类常见信号形态。

### 1. MOMENTUM：动量

动量因子在：

```text
factors/factor_momentum.py
```

核心逻辑是：

```python
px / px.shift(lookback) - 1.0
```

也就是过去一段时间的累计收益。

直觉是：过去一段时间涨得更强的股票，可能延续相对强势。

这里的 `lookback` 来自配置：

```text
settings.momentum_lookback
```

默认是 20 个交易日。

### 2. VOLATILITY：低波动偏好

波动率因子在：

```text
factors/factor_volatility.py
```

它先计算历史收益的滚动标准差，再取负号：

```text
score = -vol
```

所以这里的 `VOLATILITY` 不是“波动越大越好”，而是：

```text
数值越大 = 波动越低 = 排名越靠前
```

这样做是为了和回测层的统一规则保持一致：

```text
因子值越大，越优先进入 Top-K。
```

### 3. PE：低估值

PE 因子在：

```text
factors/factor_pe.py
```

它会用财务指标里的 EPS 和价格计算市盈率：

```text
PE = close / EPS
```

然后取负号：

```text
score = -PE
```

所以数值越大，代表 PE 越低，也就是越便宜。

这里还有一个重要细节：财务数据不是按交易日每天产生的，而是有公告日。

代码里用的是 `ann_date` 做 backward 方向的 `merge_asof`。

含义是：

```text
每个交易日，只能使用当时已经公告的最新财务数据。
```

这就是在数据层防未来函数。

### 4. ROE：盈利能力

ROE 因子在：

```text
factors/factor_roe.py
```

它同样按 `ann_date` 对齐到交易日，只使用已经公告的数据。

ROE 本身数值越高越好，所以不需要取负号。

这样四列因子最终都遵守同一个方向：

```text
因子值越大，排序越靠前。
```

这个约定非常重要。

如果有的因子是越大越好，有的是越小越好，但回测层统一按降序取 Top-K，结果就会非常混乱。

## 七、财务数据为什么要向前多取几年？

`build_four_factor_panel` 里还有一个配置：

```text
settings.fina_history_years
```

默认是 2。

它用于拉取财务指标时，向回测开始日期之前多取一些历史。

为什么要这么做？

因为回测从 2024-01-01 开始，不代表 2024-01-01 之后才允许出现财务数据。

在 2024 年初，市场上已经能看到一些更早公告的财报。

如果只从回测开始日往后取财务数据，样本开头会出现大量空值，PE 和 ROE 在前期就没法用。

所以这里向前多取历史，是为了还原当时“已经可见”的信息集。

注意，这不是偷看未来。

关键仍然是公告日对齐：

```text
交易日 t 只能使用 ann_date <= t 的财务数据。
```

## 八、为什么因子面板只构建一次？

在 `main.py` 里，因子面板会先被统一构建：

```python
panel = build_four_factor_panel(prices, long_df, settings)
```

后面单因子回测不是每次重新计算因子，而是直接取：

```python
panel[fname]
```

这样做有两个好处。

第一，减少重复计算。

四个因子只算一次，IC、单因子回测、多因子融合共享同一份输入。

第二，结果更容易解释。

如果 IC 用的是一份因子值，回测又在内部重新算另一份因子值，那么当两者不一致时，你很难排查。

现在它们都来自同一张 panel，问题定位会清楚很多：

```text
IC 不好，是评价结果不好。
回测不好，是交易规则或因子本身表现不好。
融合不好，是列权或标准化没有带来增益。
```

至少你不需要先怀疑“是不是各模块用的因子根本不是同一份”。

## 九、数据层最重要的工程纪律

这一篇的重点不在于某个因子有多强，而在于几个工程纪律：

```text
数据来源可以不同，但进入主流程的形态要统一。
长表和宽表各有用途，不要混着用。
因子面板要有统一索引和统一方向。
财务数据必须按公告日对齐，避免未来函数。
同一轮研究里，IC、回测、融合共享同一张 panel。
```

如果这些事情没做好，后面的 IC、夏普、回撤、融合曲线都可能只是建立在错位数据上的幻觉。

量化研究的第一步不是写出漂亮公式，而是先让数据在时间和标的维度上站稳。

第三篇可以用一句话收尾：

```text
先把表对齐，再让因子说话。
```

下一篇，我们再进入因子评价：IC 到底在量什么，它为什么要和回测规则分开。
