# 量化研究主链路复盘：从数据到绩效，中间到底隔了几层

前六篇，我们已经把这个 MVP 量化工程的主线走了一遍。

第一篇讲整体定位：

```text
先闭合，再加厚。
```

第二篇讲入口和配置：

```text
main.py 固定执行顺序，config.py 固定实验条件。
```

第三篇讲数据和因子面板：

```text
先把长表、宽表、panel 对齐，再让因子说话。
```

第四篇讲 IC 和多因子融合：

```text
先评价因子，再把多列信号合成一条总得分。
```

第五篇讲回测和组合配权：

```text
因子负责排序，Top-K 负责选股，配权负责分钱，回测负责账户路径。
```

第六篇讲绩效、图表和复现：

```text
净值不是终点，指标、图表和落盘才让结果可解释、可复查。
```

第七篇不再展开一个新模块。

它要做的是把前面这些层次重新放到一张地图里，回答一个更基础的问题：

> 从数据到一条可复现的量化研究结果，中间到底隔了几层？

---

## 一、为什么要把链路分层？

量化研究最容易混在一起的，是这几个问题：

```text
因子有没有预测能力？
策略历史收益好不好？
每期买哪些股票？
每只股票买多少？
手续费怎么扣？
净值曲线怎么评价？
结果以后能不能复现？
```

这些问题彼此相关，但不是同一个问题。

如果全部揉在一起，项目会很快变得难以解释。

比如：

- IC 好，不代表回测一定好。
- 回测好，不代表因子一定稳定。
- Top-K 选股好，不代表配权方式好。
- 最大夏普配权里的夏普，不等于绩效报告里的夏普。
- 净值好看，不代表权重结构健康。
- 当前跑通，不代表以后能复现。

所以这个 MVP 的核心不是“写了几个函数”，而是把研究链路拆成清楚的层：

```text
数据 → 因子 → 检验 → 融合 → 选股 → 配权 → 回测 → 绩效 → 复现
```

每一层都只回答自己该回答的问题。

这就是工程化的意义。

---

## 二、主链路总表

可以先用一张表把整个项目串起来。

| 层 | 它在问什么 | 本仓库对应 |
|---|---|---|
| 数据 | 行情、价格、财务数据是否对齐？ | `live/data_feed.py`、长表 / 宽表 |
| 因子 | 同一天里，谁比谁更值得排在前面？ | `factors/`、`panel_builder.py` |
| 检验 | 这列分数历史上有没有一点预测味？ | `analysis/ic.py`、Spearman IC |
| 融合 | 多列因子怎么合成一条总得分？ | `models/fusion.py`、z-score、IC 列权 |
| 选股 | 每期买哪几只？ | Top-K、因子降序 |
| 配权 | K 只股票里钱怎么分？ | `models/optimizer.py`、等权 / 最大夏普 / 风险平价 |
| 回测 | 现金、持仓、手续费和净值怎么变化？ | `backtest/backtest_single.py`、`backtest_multi.py` |
| 绩效 | 这条净值曲线历史表现如何？ | `analysis/performance.py` |
| 图表 | 净值、IC、权重路径是否可解释？ | `analysis/plotting.py` |
| 复现 | 这次运行以后能不能回看？ | `live/cache_io.py`、`output/cache/` |

这张表就是整个系列的压缩版。

如果你读代码迷路，可以回到这张表里问：

```text
我现在看的这个函数，属于哪一层？
它应该回答什么问题？
它不应该负责什么？
```

很多工程边界就是这样厘清的。

---

## 三、第一层：数据

数据层回答：

```text
我拿到的数据，是否能被后面的模块正确使用？
```

当前项目里，行情数据可以来自：

- 本地 CSV
- Tushare
- 合成数据兜底

但不管来源是什么，进入主流程后都要形成稳定形态：

```text
long_df：长表，一天一只股票一行
prices：宽表，一天一行，每列一只股票
```

长表适合拼财务和公告数据。

宽表适合算收益、动量、波动率，也适合回测估值。

这层最重要的风险是：

```text
对齐错误和未来函数。
```

如果财务数据用了还没公告的信息，或者因子值和价格日期错位，后面的 IC、回测、绩效都会建立在不可靠基础上。

所以数据层不是“读个文件”。

它是整个策略可信度的地基。

---

## 四、第二层：因子

因子层回答：

```text
同一天里，哪些股票相对更好？
```

当前默认因子有四列：

```text
MOMENTUM
VOLATILITY
PE
ROE
```

它们统一进入一张因子面板：

```text
date × symbol → factor columns
```

这张 panel 是后面 IC、回测、融合的共同输入。

这里有一个重要约定：

```text
因子值越大，越优先进入 Top-K。
```

所以波动率因子会取负号，PE 因子也会取负号。

这样回测层只需要统一做降序排序，不用为每个因子单独判断方向。

因子层不负责仓位。

它只负责给股票打分。

---

## 五、第三层：检验

检验层回答：

```text
这列因子历史上有没有一点预测味？
```

当前项目用的是日截面 Spearman IC：

```text
因子值@t  vs  未来 h 日收益
```

它关心的是排序关系：

```text
同一天里，因子排名靠前的股票，未来收益排名是不是也靠前？
```

IC 是因子体检报告。

它不等于交易规则。

单因子回测仍然按因子本身排序取 Top-K；IC 不直接参与当天选股，也不进入 Top-K 内的最大夏普或风险平价配权。

当前工程里，IC 有两个作用：

```text
1. 评价因子
2. 在多因子融合中提供滞后滚动列权
```

这个边界很重要。

它防止我们把“评价”“选股”“配权”混成一团。

---

## 六、第四层：融合

融合层回答：

```text
如果有多列因子，怎样合成一条总得分？
```

多因子不能直接相加。

因为动量、波动率、PE、ROE 的量纲都不一样。

所以当前项目先做：

```text
横截面 z-score
```

让每一天、每一列因子在股票池里变成相对分数。

然后有两种融合方式：

```text
等权 z-score
IC 滞后滚动列权 z-score
```

后者的直觉是：

```text
近期 IC 更好的因子，在 FUSED_ZSCORE 里说话更多。
```

但这里必须滞后：

```text
今天的权重，只能用昨天及更早的 IC。
```

因为今天的 IC 要等未来收益出来才知道。

融合层的输出仍然是一列分数：

```text
FUSED_ZSCORE
```

它像普通单因子一样进入回测。

---

## 七、第五层：选股

选股层回答：

```text
每期买哪几只？
```

当前 MVP 使用的是 Top-K：

```text
调仓日 → 因子 / FUSED 得分降序 → 取前 K 只
```

`K` 来自配置：

```text
settings.top_k
```

这层只负责确定名单。

它不负责每只股票买多少钱。

这就是“选股”和“配权”的分界线。

如果你把两者混在一起，很容易搞不清策略收益到底来自：

- 因子排序能力
- 持仓集中度
- 优化器权重偏好
- 个别股票暴露

所以当前工程明确拆开：

```text
Top-K 负责买什么。
portfolio_weighting 负责买多少。
```

---

## 八、第六层：配权

配权层回答：

```text
Top-K 里面，每只股票分多少钱？
```

当前支持三种：

```text
equal
max_sharpe
risk_parity
```

等权是基线。

最大夏普用 Top-K 股票的历史收益均值和协方差估计权重。

风险平价主要用协方差，让风险贡献更均衡。

这一层最容易混淆的是两个“夏普”：

```text
max_sharpe：调仓时用于配权的优化目标。
performance.sharpe：回测结束后对净值曲线算的绩效指标。
```

它们不是同一个对象。

当前工程也保留了回退机制：

```text
样本不足或优化失败 → 回退等权
```

这是一种很实用的工程防护。

优化器可以失败，但主流程要可解释地继续跑下去。

---

## 九、第七层：回测

回测层回答：

```text
如果历史上按这些规则交易，现金、持仓和净值怎么变？
```

当前 MVP 的回测规则是：

```text
初始现金 1.0
默认月末调仓
先卖后买
单边手续费
现金不足则缩买入
每天按现金 + 持仓市值估值
```

每次调仓还会记录：

```text
rebalance_log
```

里面包括：

```text
date
picks
weights
weighting
```

这让回测不是只有净值结果，而是有完整交易路径。

回测层暂时不处理真实券商下单、分钟撮合、滑点、涨跌停、成交量约束。

这些是后续扩展方向，不是当前 MVP 的边界。

---

## 十、第八层：绩效与图表

绩效层回答：

```text
这条净值曲线历史上表现如何？
```

当前输出：

```text
年化收益
年化波动
夏普比率
最大回撤
```

图表层负责把结果变得更可读：

```text
nav_compare：单因子 vs 融合净值
ic_compare / ic_timeseries：因子 IC 稳定性
weights_*：持仓权重路径
```

这些图不是为了好看。

它们分别回答：

- 策略曲线是否平稳？
- 因子是否阶段性失效？
- 权重是否过度集中？
- 融合是否比单因子更稳？

净值曲线只是结果之一。

指标和图表一起看，才更接近研究判断。

---

## 十一、第九层：复现

复现层回答：

```text
这次结果以后还能不能查回来？
```

当前项目在 `persist_run_outputs=True` 时会输出：

```text
output/nav_compare.png
output/ic_compare.png
output/ic_timeseries_*.png
output/weights_*.png
output/cache/prices_long.csv
output/cache/prices_wide_close.csv
output/cache/factor_panel.csv
output/cache/ic_*.csv
output/cache/run_meta.txt
output/cache/run_config.json
output/performance_summary.csv
output/rebalance_logs/*.csv
```

这让一次运行不只是终端里滚过的一段日志，而是一组可以复查的材料。

未来如果继续升级，可以加：

- 完整配置快照
- git commit
- 依赖版本
- 实验编号
- 参数网格
- 结果对比表

但 MVP 阶段先做最小落盘，已经能显著降低“结果不可复现”的问题。

## 十二、最容易混淆的几组概念

这个系列里，有几组概念值得单独拎出来。

### 1. 因子 vs 策略

因子是一列分数。

策略是一套规则。

```text
因子 + 选股 + 配权 + 调仓 + 成本 + 评价
```

合在一起，才接近一个可回测策略。

### 2. IC vs 回测

IC 评价因子排序和未来收益排序的关系。

回测模拟真实账户路径。

```text
IC 好，不等于净值一定好。
净值好，也不等于因子一定稳定。
```

两者要互相验证。

### 3. 选股 vs 配权

Top-K 决定买哪几只。

`portfolio_weighting` 决定每只买多少。

```text
买什么 和 买多少 是两层问题。
```

### 4. 配权夏普 vs 绩效夏普

`maximize_sharpe` 是调仓时的优化目标。

`performance.summarize` 里的 `sharpe` 是回测后的成绩单。

名字相似，但不要混用。

### 5. 跑通 vs 复现

跑通只是这次程序没报错。

复现是以后还能知道这次用的是什么数据、参数、因子面板、IC 和输出。

量化研究要追求后者。

---

## 十三、这个 MVP 还不是实盘系统

最后也要把边界说清楚。

当前仓库是研究侧 MVP。

它已经覆盖：

```text
数据
因子
IC
融合
回测
配权
绩效
图表
落盘
```

但它还不是完整实盘系统。

后续要接近生产，还要继续补：

- 更严格的数据治理
- 因子版本管理
- 实验追踪
- 更真实的交易成本
- 停牌、涨跌停、流动性约束
- 信号系统
- 模拟盘
- 真实券商接口
- 风控和监控

这些都很重要。

但顺序应该是：

```text
先让研究链路闭合，再逐步接执行和实盘。
```

否则策略问题、数据问题、交易问题、工程问题会全部缠在一起。

---

## 十四、结尾：先闭合，再加厚

这个系列从一开始就没有追求“大而全”的平台感。

它做的是一件更基础的事：

```text
把一条最小但完整的量化研究链路固定下来。
```

这条链路是：

```text
数据 → 因子面板 → IC → 多因子融合 → Top-K
→ 组合配权 → 回测 → 绩效图表 → 可复现输出
```

当这条链稳定以后，你后面新增任何东西都会更清楚：

- 新增因子，看它如何进入 panel。
- 新增融合方式，看它如何生成 FUSED 得分。
- 新增配权方法，看它如何只作用在 Top-K 内部。
- 新增成本模型，看它如何进入回测交易规则。
- 新增实盘模块，看它如何复用研究侧信号。

所以这个 MVP 的真正价值，不是“四个默认因子有多强”。

而是它提供了一条可以反复验证、逐步加厚的主线。

最后用一句话收束：

```text
量化工程不是先堆模块，而是先让每一层知道自己在回答什么问题。
```
